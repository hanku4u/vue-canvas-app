# Scope

## Problem

Semiconductor manufacturing engineers (process, yield, equipment, integration) routinely need to look at several data sources side by side: an SPC trend for a tool, the wafer maps for the affected lots, a table of lot history, and their own notes. Which views they need changes from one investigation to the next. Fixed dashboards don't adapt to that, and juggling many browser tabs or desktop tools loses context.

## Solution in one sentence

A web app with an infinite, pannable and zoomable canvas (in the spirit of n8n and Excalidraw) where engineers pick components from a palette, place and resize them, group them, link them through shared filters, and save the result as a canvas they can reopen and share, with view and edit control down to individual components.

## Demonstration context

This build is a **demonstration application**. It has no access to the real internal data API. A local [mock data API](mock-data-api.md) serves deterministic dummy fab data with the same shape and behavior (envelope, errors, limits, latency) the backend expects from the real one. Swapping to the real API later means changing `DATA_API_BASE_URL` and adjusting dataset YAML to the real endpoints. Nothing in the frontend changes.

## Users and roles

| Who | What they do |
| --- | --- |
| **Engineers** (primary) | Build investigation and monitoring canvases. Comfortable with data, not necessarily with code. |
| **Colleagues** (secondary) | Open shared canvases as viewers or editors and adapt them. |
| **Admin** (the project owner, possibly a few others) | Defines datasets and filter dimensions in the backend, manages permissions, and watches usage and health through the admin screen. |

Expected scale: a department, roughly 50–500 users. Some components need millions of underlying points or rows.

## Ownership

| Area | Owner |
| --- | --- |
| FastAPI backend, dataset definitions, integration with the internal data API | Project owner |
| Vue frontend | Built against the API contract in [api.md](api.md) |
| Internal data API (Iceberg, external DBs, Trino, DynamoDB) | Existing, separate team or system. Treated as an external dependency |
| Authentication | Existing upstream layer. The app only reads `x-knox-id` |

Because frontend and backend are built separately, [api.md](api.md) is the contract between them. Changes to it should be agreed before implementation, and the OpenAPI schema generated by FastAPI is the source of truth once the backend exists.

## Goals

1. Arrange any mix of components freely on an infinite canvas: add, move, resize, delete, duplicate, undo and redo.
2. Group components visually and logically. A group moves as a unit and can carry its own filters.
3. Shared filters at canvas and group level (lot, wafer, tool, chamber, step, time range, ...) that every component in scope reacts to. Selecting something in one component can set a filter for its scope.
4. All data comes through FastAPI, which calls fixed endpoints on the internal data API using admin-defined datasets.
5. Stay responsive with large data: server-side aggregation and downsampling, paged tables, and lighter rendering for off-screen or zoomed-out components.
6. Save canvases server-side and share them as viewer or editor. Restrict individual components so only certain people can see or edit them.
7. An admin screen, early in the roadmap, for managing permissions and monitoring usage and health.

## v1 scope

### In

- **Canvas:** pan, zoom, minimap, snap-to-grid, multi-select, copy/paste, duplicate, undo/redo, keyboard shortcuts. See [canvas-ux.md](canvas-ux.md).
- **Component types:** see [components.md](components.md).
  - **Chart:** trend/line, scatter, histogram, box plot, SPC control chart.
  - **Wafer map:** die x/y colored by a numeric value; single, gallery and stacked modes.
  - **Table:** server-paged grid with sort, column filters, column selection and row-selection publishing.
  - **Note:** Markdown annotation.
- **Groups** with titles, collapse, move as a unit, and group-level filters.
- **Filters:** canvas filter bar, group filters, component-level overrides, publishing from tables, charts and wafer maps. Viewers can change filters for their own session without saving.
- **Data:** FastAPI client for the internal data API, YAML-defined datasets, query shaping, caching, request coalescing.
- **Persistence and sharing:** autosave, "My canvases" and "Shared with me", viewer and editor shares, per-component view and edit restrictions, duplicate canvas.
- **Admin screen:** manage admins, browse all canvases, transfer ownership, inspect and edit shares and restrictions, see what a user can access, usage stats per dataset, slow queries, errors, data API health.
- **Identity:** from the `x-knox-id` header. No login of our own.

### Out (for v1)

- Real-time co-editing (live cursors, CRDTs). Concurrent edits are handled per component with optimistic locking.
- Drawn edges or wires between components. Shared filters cover linking.
- Freehand drawing, shapes and arrows beyond the Note component.
- File uploads and streaming or live feeds.
- Ad-hoc SQL or arbitrary API calls by users. All data goes through datasets.
- Data-level security, such as restricting which users can query which dataset. Restrictions apply to components, not data. See [permissions.md](permissions.md#what-restrictions-do-not-do).
- Editing datasets and filter dimensions in the admin UI. They are defined as code in v1.
- Mobile and touch-first layouts.

## Roadmap

Each phase ends with something an engineer (or the admin) can try.

| Phase | Outcome | Main docs |
| --- | --- | --- |
| **0. Foundations** | Monorepo, frontend and backend skeletons, CI, docker-compose with Postgres and the **mock data API** (mock API: done) | architecture, mock-data-api |
| **1. Canvas shell** | Pan/zoom canvas, palette, add/move/resize/delete, Note component, undo/redo, local-only state | canvas-ux, components |
| **2. Persistence and permissions** | Identity from `x-knox-id`, canvases in Postgres, ops-based autosave, canvas list, sharing, per-component restrictions, admin role | permissions, api |
| **3. Admin screen v1** | Admins, canvas browser, ownership transfer, shares and restrictions management, user access lookup | admin |
| **4. Data layer** | Data API client, YAML datasets, filter dimensions, `/api/query` with shaping and caching, query logging. Admin usage and health pages | data-layer, admin |
| **5. Data components** | Table, Chart, Wafer map wired to datasets, with previews for level of detail | components |
| **6. Groups and filters** | Groups, filter bar, group filters, bindings, publishing, filters in the URL | canvas-ux, data-layer |
| **7. Hardening** | Performance pass on large canvases, conflict handling UX, accessibility pass, export (if confirmed) | — |

Phases 3 and 4 can run in parallel with frontend phases 1 and 5, since backend and frontend are owned separately.

## Success criteria

- An engineer can build a five-to-ten-component investigation canvas in a few minutes without help.
- Panning and zooming stays smooth (around 60 fps) with 30+ components on the canvas.
- Changing a shared filter updates every affected component within a couple of seconds for typical queries (cached: under 300 ms).
- A shared canvas opens for a colleague exactly as the author laid it out, minus any components restricted from them.
- The admin can answer "who can see this canvas or component?" and "which datasets are slow or failing?" from the admin screen without looking at the database.
